# PMR3407 step-by-step milestone, cascade division, and presentation layer (v1)

This change lands the deterministic PMR3407 generator end to end: a zero-dependency TypeScript core that parses a movement sequence, solves it with the step-by-step (electropneumatic) method into a single `CircuitLogicalModel`, projects that model to a flat `Circuit` for validation, and derives the ladder drawing, pneumatic drawing, simulator trace, and textual explanation from that one model. The cascade method is added as an independent group-division algorithm plus a pneumatic solver. A validator refuses malformed or logically inconsistent circuits, and the renderers refuse to draw anything that fails validation. The three PMR3407 step-by-step rules and the SELO (seal) topology are realized in the solver and guarded by a mutation-based regression test. The first milestone (electropneumatic + step-by-step, seal correctness, timer relay, cycle mode) is complete with 87/87 tests green and `tsc --noEmit` clean.

Watch for: the seal-hold invariant is proven only against a **re-implemented** ladder evaluator inside the seal-regression test, not against the production simulator (`src/simulator/simulator.ts`) — the two can diverge silently (confirmed). Continuous cycle mode is generated but never simulated or asserted, so its wrap-around reset/arming is untested behavior (confirmed). The cascade last-into-first merge changes group execution order and is only method-correct under a wrap assumption that isn't validated (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The whole system hangs off one `CircuitLogicalModel` produced by a method solver. Everything downstream — the flat `Circuit`, the validator, both renderers, the simulator, and the explanation — is a projection or a trace of that model, so there is a single source of logic and the renderer never decides anything. This separation holds up under inspection.

The step-by-step solver encodes the three rules: a step's line is gated by the previous line's NO contact AND the previous movement's end-of-course sensor, held by the step's OWN relay NO contact (the seal), and dropped by the next line's NC reset contact. The seal topology is correct — a single NO contact whose driver is the relay itself.

The seal is guarded two ways: the validator rejects a model whose seal branch is missing or points at the wrong driver, and a regression test mutates the seal out and shows the memory drops. The gap is that the regression test evaluates the ladder with its own copy of the settle loop rather than the real simulator, so a regression in the production simulator would not be caught by the seal test.

Cascade group division implements the same-letter-opposite-sign rule generically with Nm = groups − 1, tested independently of any drawing. The last-into-first merge is sound as a set operation but reorders execution; the correctness argument for that reorder lives in the rules doc, not in a test.

The validator has one detectable path per claimed error class and the pipeline refuses to render when validation fails. Cycle mode is the weak spot: `single` and `continuous` produce different arming/reset topology, but only `single` is ever simulated, so continuous is generated-but-unverified.

### Seal guardrail vs the real simulator

The three rules map onto rung structure as a non-first control rung's activation branch `[prev-relay NO] AND [prev-sensor NO]` (rules 1 and 2 in series), a seal branch of the relay's own NO contact in parallel (the OR latches once set), and a reset of the next relay's NC contact in series with the coil (rule 3). When the triggering sensor opens, the activation branch goes dead and the seal branch holds the coil until the next line's NC reset opens.

The seal is defended two ways. The validator's `validateLogical` rejects any control rung whose seal branch is absent, multi-contact, driven by something other than the relay itself, or not NO — a structurally wrong seal is a `LOGICAL_CONFLICT`. Separately, `seal-regression.test.ts` mutates the seal branch out and asserts the memory drops, which makes it a real guardrail rather than a tautology: the helper returns `true` for the correct model and `false` for the mutated one, so it genuinely discriminates.

The divergence risk is concrete. The regression test does not call `runCycle`; it defines `evalLadderToFixedPoint`, a second copy of the simulator's relay settle loop, and drives the START-pulse-then-sensor-opens scenario against that copy. The comment acknowledges it is "identical to the simulator's" — but nothing enforces that identity. If `settleLadder` in `src/simulator/simulator.ts` regressed (e.g. dropped the fixed-point iteration, or evaluated solenoids in a way that perturbed relay latching), the seal test would still pass because it never touches that code. The production simulator is exercised only by the property tests, which assert reachability (every Ki energizes) and balanced-sequence end state (all cylinders home) — neither of which fails if the seal quietly stopped holding but the cycle still limped to completion via the activation branch. The fix is cheap: add one test that pulses START through `runCycle` (which already releases START and re-settles, per its `pulseStart` path), then asserts K1 remains ON after the first physical event moves A off `1S1`. That closes the loop against the real code.

### Arming the last line and cycle mode

The extra arming contact is modeled as a second contact on rung 1's activation branch, driven by the last relay: NC in single mode (armed while the last line is off), NO in continuous (the last line re-arms the first for wrap-around). Continuous mode additionally gives the last control rung a reset contact driven by the first relay. The golden test asserts this topology (arming driver = K4, NC vs NO by mode, last-rung reset present only in continuous).

What is asserted is the generated topology, not its behavior. Every simulation in the suite runs the default (single) mode. No test calls `runCycle` on a continuous model, so the wrap-around — does the first line actually re-fire after the last completes, does the first-relay reset actually drop the last line without a race in the settle loop — is unverified. Given the priority order (logical correctness first), a continuous model that generates plausible-looking rungs but doesn't cycle is exactly the kind of gap that should be closed before shipping the mode. Either simulate it or mark it explicitly out of the milestone.

### Cascade group division and the merge

The division is generic: a left-to-right scan over steps opening a new group whenever the next step's movement would put a cylinder in both directions within the current group, with `Nm = max(0, groups − 1)` and lines = groups. Parenthesized simultaneous steps and timer steps flow through the same scan uniformly, and the unit tests assert group contents and Nm on the worked exercises independently of any drawing.

The last-into-first merge is correct as a conflict check (the union of first and last group movements must not contain a cylinder in both directions) but it reorders execution: `A+A-A+` becomes `[A+ A+][A-]`, moving the trailing `A+` to the front of the first line. In cascade this is the standard optimization — the last group shares the first group's pressure line because control wraps back to it — so it is method-plausible, but the correctness argument depends on the wrap actually re-entering that line, which is asserted nowhere in code (only in RULES §A3 prose). Since no cascade simulator exists, there is no behavioral check that the merged line assignment reproduces the original movement order. Worth a targeted test or an explicit scoping note.

### Validator coverage and refusal path

Each claimed error class has a construction that triggers it and a unit test asserting the code, including the model-level checks (seal, both-solenoids-in-one-step, step-without-exit, impossible-transition on a sensor no earlier movement produces). The pipeline calls `validateCircuit` before rendering and returns `{ ok: false }` rather than drawing; the renderers independently call `assertRenderable`, so an invalid circuit cannot reach SVG. One rough edge: `assertRenderable`'s empty/malformed-circuit branch fabricates a `VAL_LOGICAL_CONFLICT` issue object with a cast instead of routing through the validator, so that one refusal reason is decoupled from the validator's logic — cosmetic, but it is the one place the guard invents a code.

### Timer delay is a fixed default

Timer steps always receive the solver's `defaultDelaySeconds` (0.3); any numeric delay written in the source sequence is discarded, not threaded into the model. RULES §A4 records this as a deliberate deferral, so it is disclosed rather than hidden — flagged here so the reviewer knows the delay shown on the timer relay is a constant, not the authored value.

### Simultaneous-group transition sensor

When a step follows a parenthesized simultaneous group, `buildPlanSteps` computes the enabling sensor as the arrival sensor of the previous step's **last-listed** movement only. For a simultaneous group whose members reach their ends at different times, gating the next step on just one member's sensor can enable the transition before the other members have arrived. The canonical-order comment suggests this is intended to be deterministic, but determinism is not the same as physical correctness here. It holds for the worked exercises (where simultaneous groups retract together), but it is an assumption worth a test that a next step waits on all arrival sensors of a simultaneous predecessor, or an explicit rule that simultaneous members are assumed co-terminal.
