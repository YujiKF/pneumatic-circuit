# Remediation of the six v1 review issues for the PMR3407 generator (v2)

This pass verifies the remediation commit (`3eac72b`) that answers the six issues raised in the v1 review. The remediation exports the production `settleLadder`, drives the seal and simultaneous-gating proofs through the real simulator, simulates continuous cycle mode (which surfaced and fixed a genuine arming bug), reconstructs cascade execution order to prove the last-into-first merge preserves movement order, pins the timer-delay deferral, and routes the render guard's malformed-circuit refusal back through the validator. All six issues are resolved on inspection; `tsc --noEmit` is clean and `node --test` reports 99/99 (up from 87/87), and I confirmed by mutation that the new proofs actually fail when the property they guard is broken.

Watch for: nothing blocking. One residual observation — the single-event physics moves all members of a simultaneous step in one round, so the AND-gating fix (issue 5) is proven only at the ladder level by manually staggering sensors, not by a physics model that lets one member arrive before another (confirmed; disclosed in RULES §A6). This is a correctly-scoped limitation, not a defect.

**Verdict**: APPROVED

## High-level view

The seal proof (issue 1) now runs the START-pulse-then-sensor-opens scenario through `runCycle` and the exported production `settleLadder`, not only the local evaluator. I confirmed it discriminates: rewiring K1's seal to the transient `1S1` contact fails the real-simulator test, and crippling `settleLadder`'s fixed-point loop fails the broader suite. The two evaluators are now pinned together instead of able to diverge silently.

Continuous cycle mode (issue 2) is simulated for the first time, and doing so exposed a real bug: the old arming put the last relay's NO contact in *series* with START on rung 1, so `START AND K_last` could never be true at rest and the cycle could never start. The fix makes the wrap a *parallel* branch — rung 1 sets on `START OR K_last OR (own seal)` — so the first press starts the cycle and the last line re-arms the first. The test asserts K1 re-fires only after K4 and that the first-relay reset drops K4 after the wrap.

The cascade merge (issue 3) now carries `mergedTailCount` on the first group and exposes `cascadeExecutionOrder`, which reconstructs physical order by running the merged-in tail at the *end* (where cascade control wraps back to line 1). Tests prove `A+A-A+` reconstructs to `A+,A-,A+` and that a non-merge case equals the original sequence — the reorder concern is retired with a behavioral check rather than prose.

Timer delay (issue 4) stays a documented deferral: the grammar has no delay token, the default (0.3 s, configurable) is what reaches the model, and RULES §A4 plus `timer-delay.test.ts` pin both the default and the threaded-configuration path so the behavior cannot drift silently.

Simultaneous-group gating (issue 5) now records every predecessor member's arrival sensor in `enableSensorIds` and the activation rung places one series `prev-sensor` NO contact per member (AND). The validator's IMPOSSIBLE_TRANSITION and STEP_WITHOUT_EXIT checks were updated to read the full set, and a real-`settleLadder` test proves the next relay stays OFF until both members arrive.

The render guard (issue 6) no longer fabricates a `VAL_LOGICAL_CONFLICT` via cast; the malformed-circuit branch moved into `validateCircuit` (which now guards missing component/connection arrays), so every refusal reason flows from the single validation path.

### Issue 1 — Seal proof through the production simulator: RESOLVED

`settleLadder` is now exported from `src/simulator/simulator.ts` (via the barrel), and `seal-regression.test.ts` adds a proof that drives the real engine: `runCycle(model, { pulseStart: true, maxPhysicalEvents: 0 })` presses START, releases it, and re-settles through the production `settleLadder`; the test then opens `1S1` by hand and calls the same production `settleLadder` again, asserting K1 is still ON and K2 is still OFF (so K1 is proven to hold on its seal alone, not because a later relay masks the drop). The `maxPhysicalEvents` cap added to `runCycle` is the seam that lets the real engine stop right after the pulse — it changes no default behavior.

I verified the proof genuinely discriminates rather than passing vacuously. Rewiring K1's seal branch to the transient `1S1` contact (`driverId: '1S1'`) fails the real-simulator test (`not ok 2`), and capping the `settleLadder` fixed-point loop to a single pass fails two tests in the broader suite. The local evaluator is retained for the mutation half, but the positive property is now checked through `runCycle` as well, so the "two evaluators can diverge silently" gap from v1 is closed — a regression in `settleLadder` that let the seal stop holding would now fail test 2.

### Issue 2 — Continuous cycle mode simulated, and a real arming bug fixed: RESOLVED

`cycle-mode.simulation.test.ts` drives `runCycle` in both single and continuous mode against the production simulator. The single test asserts K1 energizes exactly once and the cycle stops with K4 latched; the continuous test asserts K1 energizes at least twice, the second `+K1` occurs after the first `+K4`, and a `-K4` appears after the wrap (the first-relay NC reset dropping the last line).

The remediation's claim that this exposed a real bug is correct. The prior topology appended the last relay's NO arming contact into rung 1's activation branch, in series with START, so rung 1 set on `START AND K_last`. At rest `K_last` is OFF, so a single START press could never energize K1 and the continuous cycle could never begin. The fix moves the wrap to a separate parallel branch, so rung 1 sets on `(START) OR (K_last NO) OR (K1 seal)` — START starts the cycle, and after the last line completes `K_last` re-arms the first via the OR. In continuous mode the last rung also gains a first-relay NC reset so the wrap drops K4. The continuous test would fail under the old series topology (K1 would never re-fire, and `k1Ons >= 2` would break), so the regression is guarded.

### Issue 3 — Cascade merge preserves execution order: RESOLVED

`DividedGroup` now carries `mergedTailCount` (nonzero only on the first group, equal to the movement count wrapped in from the original last group), and `cascadeExecutionOrder(division)` is exported. It reconstructs physical order as `[first group's own movements] ++ [groups 2..N] ++ [first group's merged-in tail]`, modeling the cascade wrap where the merged tail runs when control returns to line 1 at cycle end. New tests prove `A+A-A+` (shape `[A+A+][A-]`, `mergedTailCount === 1`) reconstructs to `A+,A-,A+`, that the non-merge `A+B+B-A-` reconstructs to the original order with `mergedTailCount === 0`, and that no non-first group carries a tail. The v1 concern — that the merge reorders execution and the correctness argument lived only in RULES prose — is now backed by an order-reconstruction check.

### Issue 4 — Timer delay deferral pinned and disclosed: RESOLVED

RULES §A4 now states explicitly that the grammar has no numeric-delay token (only the reserved `T` marker), that a delay is never invented at parse time, and that `solveStepByStep` assigns the timer relay its configurable `defaultDelaySeconds` (0.3 s). §A4 also lists what threading a parsed per-step delay would require and marks it out of scope. `timer-delay.test.ts` pins the default (0.3 s applied to the single timer step), the caller-supplied override (1.5 s threaded through), and that non-timer steps carry no delay. This is a disclosed, tested deferral rather than a hidden constant.

### Issue 5 — Simultaneous-group AND-gating: RESOLVED

`PlanStep.enableSensorIds` records the arrival sensors of every movement of the previous step (one entry for an ordinary predecessor, one per member for a simultaneous group). The activation rung emits one series `prev-sensor` NO contact per sensor, so the branch closes only when all members have arrived (AND). The validator was updated in step with this: IMPOSSIBLE_TRANSITION now checks every sensor in the set is producible by an earlier movement, and STEP_WITHOUT_EXIT treats a step as gated if `enabledByStart`, `enableSensorId`, or a non-empty `enableSensorIds` is present. `collectSensorIds` also folds in the full set so no member sensor is dropped from the wiring.

`simultaneous-gating.test.ts` proves this three ways on `(A+B+)(A-B-)`: the model exposes both member sensors (`1S2`, `2S2`), the K2 activation branch has a `prev-sensor` NO contact for each, and the real `settleLadder` holds K2 OFF when only the first member (A) has arrived and fires K2 only once the second (B) arrives too. The staggered-arrival path is exercised by manually setting sensors because the single-event physics still advances both members in one round (Watch for; RULES §A6) — a scoping note, not a gap.

### Issue 6 — Render guard routes through the validator: RESOLVED

`assertRenderable` no longer hand-builds a `VAL_LOGICAL_CONFLICT` issue via cast. The missing/malformed-circuit check moved into `validateCircuit`, which now returns a real `LOGICAL_CONFLICT` issue when the circuit is null/undefined or lacks component/connection arrays; the guard simply calls `validateCircuit` and refuses on `!ok`. A renderer test feeds a malformed circuit through `assertRenderable` and asserts the thrown `RenderRefusedError` carries a validator-produced `VAL_LOGICAL_CONFLICT`. Every refusal reason now flows from the single validation path.

### Regressions

None found. The full suite is 99/99 green and `tsc --noEmit` is clean. The changes are additive (`enableSensorIds` alongside `enableSensorId`, `mergedTailCount`, an optional `maxPhysicalEvents` cap, an exported `settleLadder`/`cascadeExecutionOrder`) and the existing golden and property tests remain green, so the earlier single-mode and step-by-step behavior is unchanged. The two existing validator tests were updated to corrupt both the display id and the new gating list, which is correct given the validator now reads `enableSensorIds`.
